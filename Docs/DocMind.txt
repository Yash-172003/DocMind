PHASE 1

**Document Intelligence Layer**

Months 3-5 | Make the System See

Milestone: DocMind ingests any enterprise document, extracts contents intelligently, chunks appropriately, embeds, stores, and serves through an API. No question-answering yet. Just intelligent ingestion.

## **Month 3: Document Parsing and Extraction**

### **Week 9-10: Document Formats**

**Libraries to master:**

- pdfplumber - structured PDF extraction, tables, coordinates, metadata
- pymupdf (fitz) - fast text extraction from PDFs
- python-docx - Word documents
- openpyxl - Excel files
- Unstructured library - unified interface for many document types
- Azure Document Intelligence (prebuilt-layout) - go deeper on table polygon extraction

**Critical understanding:**

Why does PDF extraction produce garbage? PDFs store text as positioned glyphs, not logical paragraphs. Learn how pdfplumber reconstructs text and where it fails. Know when to use Azure Document Intelligence vs local extraction: cost vs accuracy vs data privacy trade-off.

**Build:**

An extraction layer that returns a structured representation from every document type. Test on 10 real enterprise documents. Find failure cases. Fix them or document why they cannot be fixed.

### **Week 11-12: Chunking Strategy**

Chunking is the most under-appreciated part of RAG. Fixed 512-token chunks with 50-token overlap is a naive default. Chunking strategy must depend on document type and query type.

**Three strategies to implement and compare:**

- **Fixed-size chunking - implement the naive baseline to understand its failures**
- **Semantic chunking - split on paragraph/sentence boundaries, use embedding similarity to decide breaks**
- **Structural chunking - use document structure (headings, sections, clauses) as natural boundaries**

**Papers to read:**

- Lost in the Middle (Liu et al., 2023) - why position of relevant text in context matters
- RAPTOR paper - recursive document summarization as alternative to flat chunking
- LlamaIndex node parsers docs - read every parser, understand the design choices

## **Month 4: Embeddings and Vector Retrieval**

### **Week 13-14: Embedding Models**

**Understand deeply:**

- What an embedding is mathematically - high-dimensional vector, cosine similarity
- Model differences: BAAI/bge-large-en-v1.5 vs all-MiniLM-L6-v2 vs text-embedding-3-small
- Why domain matters - general embeddings miss legal/financial nuance
- Batch embedding efficiently - never embed one chunk at a time

**Build:**

Embedding pipeline: for each chunk, generate embedding using BAAI/bge-large-en-v1.5 via sentence-transformers (local, free), store in pgvector, store raw text + metadata (document ID, chunk position, page number, section heading). Make the model configurable. Measure batch performance.

### **Week 15-16: Hybrid Retrieval**

Vector similarity fails on specific lookups. 'What is the total for PO-2024-1234?' needs exact match, not semantic similarity. Hybrid search solves this.

**Implement:**

- GIN index on chunks table for PostgreSQL full-text search (BM25)
- HNSW index on embedding column for dense vector retrieval
- Reciprocal Rank Fusion to combine dense and sparse rankings
- Reranking using cross-encoder/ms-marco-MiniLM-L-6-v2 (local, free)

**Evaluate on 20 test questions:**

| Method           | Expect                        |
| ---------------- | ----------------------------- |
| Dense only       | Good semantic, bad exact      |
| Sparse only      | Good exact, bad semantic      |
| Hybrid no rerank | Better than either            |
| Hybrid + rerank  | Best - your production config |

**Papers:**

- Original Okapi BM25 paper - understand the scoring algorithm
- Hybrid Search blog posts from Weaviate and Pinecone engineering teams (free)

## **Month 5: Generation, Citations, and API Polish**

### **Week 17-18: RAG Generation**

**Build:**

- Prompt design: structure context with \[1\], \[2\] source markers, instruct model to cite every claim
- Citation grounding: parse response, extract citations, return answer with links to original passages
- Faithfulness enforcement: if answer is not in documents, model must say so - never hallucinate

**Test edge cases:**

- Answer not in any document - model must not fabricate
- Model ignores citation instructions - fix the prompt until it does not
- Two documents contradict each other - model must surface the conflict

### **Week 19-20: Streaming, Caching, Polish**

**Add:**

- Server-Sent Events (SSE) streaming - words appear immediately, no 15-second wait
- Redis semantic caching - embed query, find similar previous queries, return cached answer above threshold
- Cache invalidation - what happens when documents are updated?

Phase 1 Complete: DocMind accepts any enterprise document, extracts it, chunks it correctly, embeds it, answers with citations in streaming fashion, and caches queries. Run evaluation suite. Document precision@k in README.

## **Month 6: Agent Foundations**

### **Week 21-22: Build From Primitives First - No Frameworks**

Do not touch LangGraph yet. Build a simple agent from scratch using only the API and Python. You must feel the pain of no abstractions so you understand what frameworks actually solve.

**Build from scratch - 3 tools only:**

An agent with: search_documents, extract_table, calculate. Receives a task, reasons about tool selection, executes tools, synthesizes an answer. Implement the full ReAct loop manually. Feel every pain point: stopping conditions, tool failures, state across steps, when to ask a human.

### **Week 23-24: LangGraph - Deep Understanding**

**Master in LangGraph:**

- Graph execution model - nodes are functions, edges are conditions
- TypedDict State management
- Conditional edges - branching based on state
- Human-in-the-loop interrupts - pause and resume workflow
- Persistence and checkpointing - resume after interruption
- Subgraphs - composing agents from smaller agents

Re-implement your primitive agent in LangGraph. Then build a Document Analysis Agent that analyzes invoices from a specific vendor in a date range and flags anomalies.

## **Month 7: Workflow Agents + Reliability**

### **Week 25-26: The Invoice Audit Agent**

A real workflow that real companies pay real money to automate. The agent receives an invoice and:

- Extracts all line items, amounts, taxes, totals
- Queries database for the associated Purchase Order
- Compares line items between invoice and PO
- Calculates discrepancies including rounding edge cases
- Checks vendor information against vendor master database
- Generates a structured audit report
- Flags items above threshold for human review
- Logs every decision with reasoning and inputs/outputs

Every edge case you hit requires an engineering decision. Document every decision you make and why. This documentation is more valuable than the code - it demonstrates systems thinking.

### **Week 27-28: Error Handling and Reliability**

**Build a reliability layer:**

- **Retry logic: exponential backoff. After 3 failures, move to fallback strategy.**
- **Fallback strategies: if OCR fails, try alternative extraction method.**
- **Stuck detection: if agent takes more than N steps without progress, interrupt.**
- **Confidence scoring: agent rates its own confidence. Below threshold triggers human review.**
- **Full audit trail: every tool call, reasoning step, decision logged with timestamp.**

## **Month 8: Human-in-the-Loop + MCP**

### **Week 29-30: Human-in-the-Loop Design**

Full automation is a lie for enterprise AI. The real goal: automate what can be automated reliably, escalate what cannot.

**Build a HITL interface:**

- When agent flags a discrepancy: pause execution using LangGraph interrupt
- Send webhook notification to reviewer
- Present discrepancy via simple web UI
- Wait for human approval, rejection, or modification
- Resume execution based on human decision
- Log human decision, context, and reasoning

### **Week 31-32: MCP (Model Context Protocol)**

Read the full MCP specification at modelcontextprotocol.io - the actual spec, not a tutorial. Understand: Resources, Tools, Prompts, client-server architecture, transport mechanisms (stdio, HTTP with SSE).

**Build an MCP server for DocMind exposing:**

- Resource: documents:// - browse and read documents in the system
- Tool: search_documents - semantic search across all documents
- Tool: extract_entities - named entity extraction from a document
- Tool: run_audit - trigger the audit agent on a document pair

Test by connecting to Claude Desktop or any MCP-compatible client. Your system is now accessible to any AI that speaks MCP.

PHASE 3

**Reliability Engineering**

Months 10-12 | Make the System Know When It's Wrong

This phase separates you from 90% of AI engineers. Most can build features. Almost nobody can systematically tell you whether those features are working correctly. You will build that capability.

## **Month 10: Evaluation Systems**

### **Week 37-38: Evaluation Theory**

**Papers to read:**

- Ragas: Automated Evaluation of Retrieval Augmented Generation
- Measuring Massive Multitask Language Understanding - how to design evaluation datasets
- DeepEval documentation - understand every metric they implement

**Core evaluation dimensions:**

Retrieval quality: Precision@k, Recall@k, MRR

Generation quality: Faithfulness (answer uses only retrieved context), Answer relevance, Context relevance

**First build - the evaluation dataset:**

For your test documents: write 50 questions requiring retrieval. Write ground-truth answers. Identify which passages contain the answer. This is hard. It takes time. It is extremely valuable. Having a hand-crafted evaluation dataset is the difference between knowing your system works and hoping it does.

### **Week 39-40: Automated Evaluation Pipeline**

**Build a pipeline that runs with one command in under 10 minutes:**

- For each question in your 50-question dataset, run DocMind's full pipeline
- Evaluate retrieval: did correct passages appear in top-k?
- Evaluate generation using Ragas metrics
- LLM-as-judge comparison against ground-truth using Ollama (local, free)
- Store all results in PostgreSQL with timestamp
- Generate report: current vs last run vs best ever

Add to GitHub Actions: runs automatically on every push. This is your regression safety net.

## **Month 11: Observability and Tracing**

### **Week 41-42: Langfuse Observability**

Deploy Langfuse via your docker-compose (self-hosted, MIT-licensed, free). Instrument every LLM call and agent step in DocMind.

**Trace for every query:**

- Every LLM call: exact prompt, response, latency, token count, cost
- Every retrieval call: query, results, scores, latency
- Every tool execution: tool name, input, output, latency, success/failure
- Every agent step: state before, action, state after

When something goes wrong in production, you can answer: exactly what happened, at which step, with what input, producing what output.

### **Week 43-44: Hallucination Detection**

**Four approaches - implement all four:**

- **Retrieval grounding check: does each claim in the answer appear in retrieved chunks?**
- **Self-consistency: run same question multiple times, check if answers are consistent**
- **NLI-based faithfulness: use local NLI model to check if answer is entailed by context**
- **LLM-as-judge: use Ollama (local, free) to evaluate faithfulness against retrieved context**

Flag answers where confidence is low. Store hallucination scores. Alert when rate exceeds threshold. This is how production AI systems stay trustworthy.

## **Month 12: Prompt Versioning and A/B Testing**

### **Week 45-46: Prompt Versioning**

Prompts are code. Version them like code.

- Every prompt stored in database with a version number
- Changing a prompt creates a new version - never overwrites
- Every LLM call logs which prompt version was used
- Roll back to any previous version with one command
- Evaluation pipeline compares performance across versions

### **Week 47-48: A/B Testing**

- Route X% of traffic to version A, Y% to version B
- After N queries: compare evaluation scores, cost, latency
- Promote winner or roll back loser with one command

Phase 3 Complete: DocMind knows with quantitative precision how well it is performing. Retrieval metrics, generation quality scores, hallucination rates, cost dashboards, full traces, and prompt versioning. This is what separates production systems from demos.

## **Month 13: Kubernetes on Azure**

### **Week 49-52: Real AKS Deployment**

**Kubernetes to master:**

- Pods, Deployments, Services, Ingress - the core objects every engineer must know
- ConfigMaps and Secrets - never hardcode configuration or credentials
- Horizontal Pod Autoscaling (HPA) - scale DocMind based on CPU and request load
- Resource limits and requests - prevent one service from starving others
- Liveness and readiness probes - Kubernetes needs to know your app is alive
- Rolling deployments and rollback - zero-downtime updates
- Helm charts - package your entire application for repeatable deployment

**What to deploy on AKS:**

- DocMind FastAPI app - 2+ replicas with HPA
- Azure Database for PostgreSQL - managed, free tier available
- Azure Cache for Redis
- Langfuse - observability, deployed via Helm
- Nginx Ingress with TLS - real HTTPS
- GitHub Actions CI/CD - evaluation suite on every push, deploy on merge to main

Cost control: Use \$200 Azure free credit. After it expires, run for 1 more month (~₹800-1,500) to finish. Then delete the cluster. Total: under ₹1,500 for a skill that every senior company expects.

## **Month 14: Async Processing and Scalability**

### **Week 53-56: Queue-Based Document Processing**

Document processing is slow. Users cannot wait 60 seconds for a PDF to be processed. Queue-based async architecture solves this.

**Concepts to master:**

- Message queue patterns: producer/consumer, fan-out, dead letter queues
- Celery for distributed task processing
- Azure Service Bus as production message broker
- Worker scaling based on queue depth
- Task retry with exponential backoff and dead letter handling

**Refactor DocMind to fully async:**

- POST /documents/upload returns job ID immediately - acknowledges upload in < 100ms
- Document placed on Azure Service Bus queue
- Workers pull from queue and process documents in parallel
- Status updated in real-time as each processing step completes
- Workers scale automatically based on queue depth
- Failed jobs go to dead letter queue for manual review

Phase 4 Complete: DocMind is cloud-deployed, queue-based, autoscaling, and production-grade on Azure Kubernetes Service. You have built and operated the complete stack end-to-end. This is what the resume says now.

## **Daily Structure**

| Block                        | What                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| Deep Work 1 (3hr, morning)   | Primary learning or building. One topic. No context switch. |

## **Weekly Structure**

- **Monday: One concrete deliverable for the week. Not a learning goal. A build goal. 'I will have X implemented by Friday.'**
- **Wednesday: Architecture review. Draw your system on paper. What breaks at 10x load? What happens when the LLM returns garbage? What is not observable?**
- **Friday: Write a short technical note about something you understood this week that you did not understand before.**
- **Weekend: Deep reading. Papers, books, engineering blogs. One deep read, not ten shallow skims.**

## **Monthly Structure**

- Build something small completely outside your current project. Forces new neural pathways.
- Read one post-mortem from a production AI system failure. Understand exactly why it failed.
- Identify the thing you have been avoiding learning. Do that thing.
- Review your confusion log. What patterns do you see? What gaps remain?

## **How Elite Engineers Actually Think**

- **Systems not features. First question: 'what are the failure modes?' Not 'what code do I write?'**
- **Source code not docs. When LangGraph surprises you, open the LangGraph source.**
- **Observability first. Every system starts with: how will I know this is working correctly?**
- **Debug like a scientist. Hypothesis → test → observe → update model. Never randomly change things.**
- **Genuine theories. Not 'I know how to use X' but 'here is my model for why X succeeds or fails.'**
